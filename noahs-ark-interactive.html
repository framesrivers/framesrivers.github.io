Why five reporting screens?
Only two collect information. Both report types use the same short structure; Review checks what becomes public before submission.
Prototype behavior
Enter or edit a report, preview and share a flyer, create a demo profile, and try community posts, likes, and replies.
Design prototype. Reports, demo accounts, and community posts are kept only during this session. Nothing is published publicly or sent to shelters or neighbors.
Development handoff notes
  • Persist a report before showing confirmation. If submission fails, keep answers and offer retry on Review.
  • Guest reporting needs a verified return link or code so the owner can edit or close the report later.
  • Production sign-in requires secure authentication and account recovery. Production community posts need persistence, moderation, and abuse reporting; the preview stores neither real accounts nor public posts.
  • The map shown here is illustrative; the text field is the working path. Build a real map only if location selection is added.
  • Require pet type, an approximate area, a contact number, and either a photo or description. Found reports also need custody or sighting status. Validate phone format on device and server.
  • The simple flyer shows a number only with explicit consent. A private contact option needs a public contact page, messaging or relay, notifications, and abuse controls.
  • Localize every fixed string for the Spanish release. In this preview, only flyer labels translate; the owner's description stays as entered.
  • Use native safe areas and Dynamic Type text styles, maintain 44pt touch targets, and check larger text on smaller phones. Do not claim automatic alerts or shelter outreach until those integrations exist.
